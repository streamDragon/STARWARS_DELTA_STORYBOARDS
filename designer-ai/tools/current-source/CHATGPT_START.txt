IDENTITY
- cast[].id is a local script reference used by actions/dialogue/continuity inside this movie only; it does not redefine canonical character identity.
- cast[].identityHandle is the exact CURRENT canonical/preferred route=Actor authoring identity and is the persistent identity used for identity-sensitive checks and dialogue.
- cast[].materialHandle is the exact CURRENT movie-local visual material route for a technically legal Sprite or direct simple SpriteSequence/Animation performer. It does not create persistent Actor identity and it is not valid for dialogue participants.
- A non-dialogue movie-local performer may use materialHandle without being one of the published persistent Actor identities; do not impose an Actor-count limit on such performers.
- Never duplicate the same identityHandle under multiple cast ids as if they were distinct Actors. If multiple cast entries intentionally represent clones/repeated instances of one canonical Actor Identity, declare one root cast member and set every additional instance's sameIdentityAs to that root (or to a valid chain ending at that root). Truly distinct characters require distinct identityHandle values from CURRENT.
- visible[].handle selects the visible representation.
- actions[].subject references cast[].id.
- animationHandle is the primary animation selector: it chooses one exact technically-authorable CURRENT direct Animation material, independently of Actor ownership. Once selected for a cast subject, that exact handle remains the active visible animation across later consecutive beats while the same subject remains visible, until another explicit animationHandle replaces it. Repeating the same handle on each visible QA beat is allowed for clarity. animationIntent is legacy/secondary and is omitted unless CURRENT explicitly exposes a supported relationship. performanceIntent remains descriptive directing intent. Never author raw AnimationClip IDs.
- Sprite frames, portraits, textures, animation frames and raw Catalog IDs do not become Actor identity because they look related.
- If a persistent/dialogue Actor is requested and CURRENT does not expose a legal Actor handle, that Actor identity is unavailable for direct authoring. This does not prevent a non-dialogue movie-local performer from using a legal CURRENT materialHandle.

STORY AND EVIDENCE
Every production beat needs a clear audience-observable purpose. Dialogue or a title saying an event happened does not implement the visible event.

VISIBLE EFFECTS / PARTICLES
- A legal route=Effect item in visible[] is already an audience-visible obligation.
- Do not add meaningless reveal/activate actions merely to wake up an Effect.
- repeated identical Effect handles remain distinct authored instances.
- Effect timing uses visible[].startOffsetSeconds / visible[].durationSeconds when present.

- Particle/prefab lifecycle is Unity-owned; authoring expresses the visible obligation, not the low-level particle component wiring.

ACTOR IDENTITY, DIRECT ANIMATION AND MOTION
- Actor identity and Animation material are separate. Actor handles answer WHO/WHERE; Animation handles answer WHAT VISIBLE SPRITE ANIMATION PLAYS.
- Animation and movement are separate and may run simultaneously.
- For visible Sprite animation, prefer one exact CURRENT animationHandle from directAnimationMaterials / ANIMATION_RETRIEVAL_INDEX. Choose it using previewUrl and semanticFacets. Direct simple-Sprite animation material does not require Actor ownership.
- animationIntent is legacy/secondary authoring. Do not use it unless the matching CURRENT explicitly publishes a supported relationship for that exact use.
- performanceIntent is descriptive directing intent only; it never selects or guarantees an Animation clip.
- CRITICAL FIELD SEPARATION: walking is not motionIntent=walk. Spatial walking is type=move + motionIntent=move; the visible gait, when needed, is selected by an exact published walk animationHandle. Never copy animation meaning into motionIntent unless that literal independently exists in the schema motionIntent enum.
- never infer appearance or animation behavior from an Actor name, prefab name, filename, or role. Inspect the Animation preview when appearance matters and use semanticFacets only as descriptive retrieval metadata.
- actor motion uses only schema-legal motionIntent/path fields.
- exact path geometry uses the schema's pathShape/pathPoints fields when needed.
- pathPoints[] is canonical JSON object geometry: every point is exactly {"x": 0.1, "y": 0.3}-style with numeric x/y fields. Tuple/array forms such as [x,y] are forbidden.
- semantic speed is only slow, medium, fast or burst.
- Actor Orbit remains fixed-center while the matching runtime capability requires it.
- do not assume pursuit/escort/intercept means per-frame moving-target tracking unless CURRENT/runtime explicitly supports it.

ACTION TIMING
- actions[].startOffset is optional seconds from beat start.
- actions[].duration is optional action duration.
- explicit intervals must remain legal and inside the owning beat.
- actions[] array order is never hidden sequencing.
- use explicit intervals for staggering/concurrency.
- use adjacent beats for distinct semantic movement phases unless one continuous precise path intentionally represents the whole movement.

53 FIRST-CLASS CINEMATIC MOVES

CAMERA
Camera authoring is semantic directing intent.
- framing/movement/subject/direction/intensity/parallax use only matching schema values.
- camera.intensity is a closed enum with exactly subtle, medium, strong. Do not use low/high here; those words belong to other fields in the schema and are not interchangeable.
- camera.subject is semantic composition intent and is not automatically a physical Transform target.
- Hold may preserve semantic composition without a physical target.
- Follow/Track may bind an active legal WorldActor when runtime support exists.
- Pan supports left/right/up/down reveal; up/down is the current 2D tilt-style reveal route.
- camera.parallax moves legal physical scenery layers with depth-scaled offsets and never moves UI/Overlay; locked dialogue remains stable.
- Push/Pull mean continuous within-shot framing change, not merely a cut to another static lens size.
- Drift/Pan/Shake/ImpactShake must be visibly meaningful when Unity executes them; technical non-zero movement that is imperceptible is not exact success.
- Camera Orbit is not a legal Simple V1 camera movement in this CURRENT. Use Actor motionIntent=orbit for fixed-center Actor Orbit; never invent an unseen 3D side/back view.
- locked portrait dialogue defaults to stable legal coverage; do not mix unsupported world-camera motion into a locked dialogue beat.

DIALOGUE
Dialogue is closed-world.
- speaker/listener must reference an existing cast[].id exactly.
- Resolve that local cast id first, then validate the referenced cast[].identityHandle against EMOTIONAL_DIALOGUE_CURRENT.
- cast[].id does not need to equal the published actorId or identityHandle; it is only a local movie reference.
- Unknown or misspelled speaker/listener aliases are errors. Never fuzzy-match or silently reinterpret them as direct identities.
- dialogue cast identityHandle must equal a published authoringReady dialogue character identityHandle.
- expressionIntent is opt-in, not a per-line default. Omit it for ordinary dialogue and let the exact CharacterPack published defaultExpression apply. Add expressionIntent only for a deliberate visible acting beat; then resolve speaker -> cast[].identityHandle -> the exact authoringReady dialogue character and require the token to appear literally in that character supportedExpressions. Never auto-generate Determined/Concerned/Urgent/Relieved/Shocked/Neutral from dialogue wording, mood or delivery. If the desired expression is absent, omit expressionIntent.
- do not invent identity, expression or presentation values from generic Catalog evidence.

AUDIO
- each authored cue uses kind + exact CURRENT route=Audio handle.
- repeated uses remain separate authored occurrences.
- visual Effects and projectiles do not automatically supply sound.
- generated simple_audio_* identities are backend-only.

SILENT AUDIO POLICY
- Audio is optional in CUTSCENE_SCRIPT_V1. A silent cutscene is legal.
- When CURRENT exposes zero route=Audio handles, omit beat.audio entirely. Never invent or infer an audio handle.
- Missing/unavailable CURRENT audio is a non-blocking YELLOW warning: AUDIO_UNAVAILABLE_IN_CURRENT. It must not block schema validation, Editable Preview or Build.
- If an explicit audio cue is authored, its handle must still be an exact CURRENT route=Audio handle; an explicit invalid/fabricated cue remains an authoring error.
- For a requested full cinematic scene, when CURRENT exposes suitable Layer/Effect/Audio handles, deliberately establish location, atmosphere and timed accents instead of leaving the scene visually empty. This is authoring guidance, not a blocker: intentionally minimal or silent films remain legal.

CUTSCENE PROJECTILES / MISSILES
- every type=fire action requires a schema-legal projectileId.
- projectileId is closed-world and comes from the matching schema.
- count is a real authored quantity.
- projectile identity is never an Effect handle, filename, gameplay prefab name or fuzzy match.
- target/anchor intent must remain exact when authored.
- launcher, muzzle transform, collider wiring, travel mechanics and Timeline receiver implementation remain Unity-owned.

CONCURRENCY
The system must support legal simultaneous operations rather than serializing them merely to avoid conflicts. Examples include:
- actor animation + actor movement;
- actor animation + camera movement;
- moving shooter + fire;
- two-way fire + camera shake;
- camera framing change + a separate compatible perspective property.
One runtime property/capability still has one effective owner for the same interval.

ACCEPTED FIXTURE / BACKEND REPAIR DISCIPLINE
Once a legal CUTSCENE_SCRIPT_V1 fixture passes authoring integrity, downstream BACKEND/ENGINE failures are repaired against that same authored fixture.
- do not rewrite legal beats/timing/handles/camera intent/animation intent/projectile counts/targets merely to hide runtime failure;
- fixture names, beat IDs, actor IDs and timestamps never become production special cases;
- compile-only success is not movie-quality proof;
- runtime PASS requires actual Unity execution of the final saved/reopened Editable Preview.

FAIL-SOFT DISCIPLINE
