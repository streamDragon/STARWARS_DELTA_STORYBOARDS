ACTOR IDENTITY CONTRACT - REQUIRED
- cast[].id is the logical Actor id used by actions/dialogue/continuity. It is not an asset handle.
- cast[].identityHandle MUST be the canonical/preferred CURRENT Actor authoring identity for that person/entity, using route=Actor and authorableInSimpleV1=true.
- For normal WORLD ACTORS, use the exact deterministic authoring handle exported by CURRENT/AUTHORING_HANDLES. The expected authoring shape is <name>__<runtimeHash>.
- NEVER put a raw Unity/Catalog runtime id shaped like GUID:fileId (for example 6ecabe6e...:2864309899...) into a world Actor cast[].identityHandle. That is backend identity evidence, not a CURRENT deterministic authoring handle.
- Curated dialogue is the explicit exception: when EMOTIONAL_DIALOGUE_CURRENT publishes an identityHandle for an authoringReady dialogue actor, use that exact published identityHandle even when it is actorId-shaped rather than <name>__<runtimeHash>.
- visible[].handle selects the visible representation for that visible obligation. A Sprite frame, Texture, portrait frame, animation frame or other visual record may be legal there when CURRENT permits it, but it MUST NOT be substituted for cast[].identityHandle.
- actions[].subject references cast[].id for Actor actions. Do not put an asset handle in actions[].subject.
- animationIntent and performanceIntent are semantic requests such as walk or look_up. Never author a raw AnimationClip id/handle.
- A visual/frame record that belongs to an Actor does not itself become the Actor identity. The backend may canonicalize legacy visual handles, but authors must still prefer the published canonical Actor handle.
- If CURRENT does not expose a legal canonical Actor identity for a required world character, do not infer one from filenames, folders, frame names, sprites, GUID:fileId values or old JSON. Treat the Actor as unavailable for world-authoring until CURRENT exposes it.

STORY / EVIDENCE
Every production beat should have a clear storyClaim and non-empty evidence. evidence describes audience-observable proof, not backend bookkeeping.

VISIBLE EFFECTS
- A legal route=Effect item in visible[] is an audience-visible beat obligation.
- Do not add meaningless reveal/activate actions merely to force an Effect to exist.
- Multiple authored instances using the same Effect handle remain distinct obligations.
- A projectile or impact does not implicitly satisfy an unrelated Effect request.
- visible[].startOffsetSeconds is optional for Effect obligations and is measured from the containing beat start. Omitted means beat start.
- visible[].durationSeconds is optional for Effect obligations. Omitted means from the resolved Effect start through beat end; explicit duration is clamped to beat end.
- Effect startOffsetSeconds must be finite and >= 0. durationSeconds must be finite and > 0. A resolved Effect start at or after beat end is invalid.
- Effect overlaps are legal. Repeated identical Effect handles remain distinct generated instances and must never be deduplicated by handle.
- These Effect timing fields are not action timing fields: Effect uses startOffsetSeconds/durationSeconds; actions use startOffset/duration.

MOTION / COMPOSITION - CURRENT CINEMATIC MOTION TOOLKIT
- Screen coordinates use normalized Unity viewport convention: (0,0)=bottom-left, (1,1)=top-right, center=(0.5,0.5). X increases right; Y increases up.
- Never use browser/image top-left coordinates. (0.92,0.12) is lower-right.
- Do not calculate pixel positions and do not invent Unity world coordinates. The backend resolves viewport-authored motion against the active Cutscene camera.
- Existing semantic motionIntent values remain legal. Actor Orbit remains fixed-center unless CURRENT runtime explicitly expands it. Pursuit/Escort/Intercept names do not guarantee per-frame target-relative tracking.
- Precise geometry uses motionIntent="path_loop" with type="move" and a legal pathShape. All precise paths lower to the existing V5 FollowPath owner; do not invent another motion system.

WAYPOINTS
- pathShape="waypoints" requires pathPoints.
- Author 2..32 exact viewport points.
- pathPoints use objects {"x": number, "y": number}.
- x/y may extend from -0.25 to 1.25 for deliberate cinematic offscreen entry/exit.
- Example evasive route: (-0.10,0.40) -> (0.24,0.66) -> (0.46,0.30) -> (0.72,0.70) -> (1.10,0.52).
- Use waypoints for exact corners, jinks, slaloms and hand-authored screen trajectories.

BEZIER
- pathShape="bezier" requires pathPoints.
- Exactly 3 points means quadratic Bezier.
- Exactly 4 points means cubic Bezier.
- Use Bezier for cinematic swoops, hooks, banking turns, dives, pull-ups and asymmetric curves.
- Example cubic swoop: (-0.10,0.72), (0.22,0.18), (0.68,0.22), (1.10,0.68).

ACTION TIMING
- pathEasing is legal for open path traversal: linear, ease_in, ease_out, ease_in_out, smooth_step.
- startOffset is an optional ACTION field measured in seconds from the owning beat start.
- duration is an optional ACTION field measured in seconds for that action.
- Keep startOffset >= 0, duration > 0 and keep every explicitly timed action interval inside the owning beat.
- Use different startOffset/duration values to stagger concurrent actions such as multiple ships or timed fire instead of making every action start simultaneously.
- Explicit action timing does not make actions[] array order a sequencing language. Never assume first array item runs before the second unless their authored intervals actually establish that relationship.
- A single precise waypoints/bezier action may encode a multi-turn continuous movement. Distinct semantic locomotion phases such as approach -> pass_camera -> bank_away should still use adjacent beats unless represented deliberately as one continuous path.
- These action fields are not the same as root/beat durationSeconds and are not the same as visible Effect startOffsetSeconds/durationSeconds.

SEQUENTIAL MOTION
- A single precise waypoints/bezier path may encode a multi-turn continuous movement inside one action.
- Separate semantic locomotion phases such as approach -> pass_camera -> bank_away should still use adjacent beats unless they are deliberately represented as one precise continuous path.
- Do not assume array order creates hidden action sequencing.

TRAJECTORY
- trajectory remains semantic style guidance: linear, arc, curve, orbit_like, zigzag, drift, screen_parallax.
- trajectory alone is not a precise geometry definition. Use pathShape/pathPoints when exact screen geometry matters.

CAMERA
- camera.subject is semantic composition intent by default. Follow/Track may bind a legal active WorldActor only when runtime support exists.
- Camera orbit is a 2D/2.5D composition concept and does not imply invented 3D geometry.

DIALOGUE
- Dialogue is closed-world.
- speaker/listener must be exact authoringReady actorId values from EMOTIONAL_DIALOGUE_CURRENT and match cast[].id.
- dialogue cast identityHandle must be the exact published identityHandle for that actorId.
- expressionIntent is exact and case-sensitive. Omit it to use the published defaultExpression.
- LOCKED DIALOGUE CAMERA RULE: default every locked dialogue beat to camera.movement="hold". Do not author push, pull, follow, track, drift, shake, impact_shake or orbit inside a locked dialogue beat. Use camera.movement="cut" only when the matching CURRENT validation explicitly allows cut-based coverage for that presentation.
- Until CURRENT explicitly declares dialogue overlay-safe, keep world locomotion out of dialogue beats.

AUDIO
- Each audio cue uses kind + exact CURRENT route=Audio handle.
- Use sfx for discrete events, ambience for environmental beds and music for score.
- startOffsetSeconds is relative to the beat and must remain inside it.
- Visual Effects and projectiles do not automatically supply sound.
- Never author generated simple_audio_* identities.
- Repeated use of the same legal Audio handle is allowed. Each authored cue remains a distinct occurrence with its own beat/startOffset/duration; never deduplicate or merge repeated cues merely because the Audio asset handle is identical.
