============================================================
CLOSED-WORLD AUTHORING - MANDATORY
============================================================

Use only assets, IDs, capabilities, compatibility mappings and visual evidence that exist in the CURRENT STARWARS_DELTA publish resolved from OPEN_CURRENT.json.

1. Never invent, approximate, substitute, hallucinate or remember an asset because it would make the scene nicer.
2. Never mix old Catalog IDs, old JSON IDs, old Instruction Books, old screenshots or another publish transaction into new authoring.
3. Use exact legal destinations: Actor -> cast/world actor; Layer -> background/scenery; Effect -> effect; Ui -> dialogue/UI; Animation -> exact compatible animation; Audio -> audio.
4. A Visual Atlas ID, screenshot ID or representative image is not automatically a runtime Actor ID.
5. For important elements preserve the chain: VISUAL EVIDENCE -> CANONICAL/AUTHORING ID -> LEGAL ROLE/CAPABILITY.
6. If CURRENT lacks an optional ideal asset, finish with the best legal CURRENT composition. If an essential visual cannot be represented honestly, report one explicit Asset Gap instead of synthesizing it.

============================================================
PRODUCTION STORYBOARD - HARD INVARIANTS
============================================================

V3_EXACT_ASSET_STORYBOARD_REQUIRED
A production storyboard intended to predict Unity may contain only exact CURRENT visual evidence. Every visible principal object must have provenance back to CURRENT Catalog/Director + Atlas evidence. Use the real source pixels. Do not redraw, beautify, restyle, clean up, anime-ify, change view angle, or replace the asset with a visually similar object.

V3_GENERATED_STORYBOARD_ART_FORBIDDEN
Image generation or redrawn art is not production storyboard evidence. It is allowed only when the user explicitly requests concept/reference art, and it must be labelled CONCEPT / REFERENCE ART - NOT CATALOG EVIDENCE.

V3_MISSING_VISUAL_MUST_REMAIN_GAP
When a requested visual does not exist, exactly three responses are legal: choose another composition using available assets; choose another exact CURRENT asset that genuinely serves the same function without changing identity; or emit MISSING ASSET / GAP. Never synthesize the missing object.

V3_STORYBOARD_JSON_ASSET_MISMATCH
For significant cinematic work, author in this order:
CURRENT -> inspect real visual candidates -> production storyboard/shot plan -> visual approval when appropriate -> JSON using the SAME asset identities.
A principal storyboard asset and the corresponding JSON asset must not silently diverge. If they differ, flag the mismatch and repair one side deliberately.

A tiny top-view fighter remains a tiny top-view fighter. Do not redraw it into a cinematic side-view ship. If no eye close-up exists, there is no eye close-up; use an available portrait/expression or choose another shot.

- catalogRevision

- schemaHash

============================================================
VISUAL ACCESS HONESTY - NON-NEGOTIABLE
============================================================

Before the first visually grounded choice, storyboard panel or VISUAL_VERIFIED claim, establish whether the actual CURRENT Atlas pixels can be rendered and inspected.

Metadata is not visual inspection. None of these prove appearance: displayName, tags, description, source path, asset ID, atlas page, atlas slot, binary access or a PDF URL.

Required visual-verification chain:
OBSERVED PIXELS -> EXACT ATLAS PAGE/SLOT -> EXACT VISUAL REFERENCE ID -> EXACT CANONICAL/AUTHORING RUNTIME ID.

If the public Atlas cannot actually be rendered by the current ChatGPT tool path, say so immediately. If the task requires visual selection, ask the designer to upload only STARWARS_DELTA_CHATGPT_VISUAL_ATLAS_CURRENT.pdf. Do not ask for Catalog ZIPs, category PDFs, source files or the large Visual Library merely to obtain pixel access.

============================================================

For substantial cinematic work:
1. Resolve CURRENT and its atomic identity.
2. Search the relevant Director categories instead of reusing familiar assets by habit.
3. Inspect actual pixels for visually important candidates.
4. Build the story, shot grammar and exact-asset storyboard/coverage plan.
5. Obtain visual approval when appropriate.
6. Serialize the approved plan into JSON using the same exact asset identities.
7. Run Film Preflight and the no-error JSON preflight before delivery.

The storyboard and JSON are one film expressed twice, not two independently invented movies.

============================================================
ACTOR IDENTITY AND CAST
============================================================

Cast is identity. Animation/action frames do not manufacture new identities.

- cast[].visualAssetId must resolve to a legal Actor-primary/canonical identity.
- Prefer the Director's canonical/preferred Actor identity where provided.
- Do not use Run/Hit/Death/Walk/Launch frames as persistent cast identity merely because they show the desired pose.
- Distinct named Person characters require distinct resolved preferred Actor identities unless intentionally representing the same identity/clone.
- Do not create six differently named extras around one normalized Person identity. Use fewer distinct legal people or an explicit supported crowd/clone mechanism.
- World/cast identity and UI portrait identity are separate roles.

============================================================
ANIMATION COMPATIBILITY IS EXACT
============================================================

PlayAnimation is legal only when the exact animationAssetId appears in the exact selected Actor's CURRENT compatibleAnimationIds.

Never infer compatibility from filename, family name, package, visual similarity or semantic wording.

If no exact compatible animation exists: choose another compatible animation, use static/Move/Hold presentation when legal, or report a gap. Never bind motion from a visually similar character/robot.

For a running world character, use both exact compatible PlayAnimation(Run) and Move when both are legal. Move alone slides a mannequin; animation alone runs in place.

============================================================
DIALOGUE PRESENTATION INVARIANTS
============================================================

- Cast identity remains Actor-primary/canonical. Portrait/body/frame assets are presentation sources, not cast identity.
- Dialogue-only participants use presentationMode=DialoguePortrait and spawnWorldActor=false.
- presentationMode=Both is legal only when explicitly authored and world representation is temporally isolated from portrait representation. Never infer Both.
- FACE_TO_FACE_PORTRAITS participants cannot simultaneously remain active as world actors in the same locked-dialogue window.
- Each visible participant has one primary source: portrait XOR body, not both.
- SUBTITLE_ONLY carries no portrait/body participant visuals.
- Locked dialogue requires owning shot actorActions=[].
- Locked dialogue camera is Hold, supported Snap, or supported cut-based presentation only. No continuous Push/Pull/Zoom/Pan/Follow/Track/Drift/Orbit merely for decoration.
- Portrait close-ups, speaker focus, two-shot and reaction cuts are valid 2D cinematic variety when legal visual sources exist. Do not invent nonexistent facial close-ups.

Preserve/obey current diagnostics including:
DIALOGUE_ACTOR_PRESENTATION_CONFLICT
DIALOGUE_VISUAL_SOURCE_CONFLICT
DIALOGUE_VISUAL_SOURCE_UNSUPPORTED
CUTSCENE_DIALOGUE_CAMERA_MOTION_FORBIDDEN

============================================================
DESTINATION CAPABILITY BEATS VISUAL RESEMBLANCE
============================================================

A visible picture is not automatically legal in every field.

- ShowUi requires an exact Ui-legal record.
- Layer actions require Layer legality.
- Asset-backed effects require Effect legality.
- Animation fields require Animation IDs.
- Audio fields require Audio records.
- A portrait-looking sprite is not a world Actor unless CURRENT explicitly proves Actor legality.
- A UI-looking sprite is not ShowUi-legal just because it looks like UI.

Prefer canonical direct authoring over relying on auto-repair. Automatic repair is a safety net for old/bad input, not a strategy for new ChatGPT output.

============================================================
SYSTEM-MANAGED PROPORTIONS AND BACKGROUNDS
============================================================

When systemManagedProportions=true, authored scaleX/scaleY default to 1.0. Unity owns semantic normalization. Do not enlarge a tiny source image by 8x because framing is broken. Wrong asset, wrong presentation, wrong camera coverage and wrong scale are separate problems.

Background/ FarBackground assets must visually function as the intended location. Do not stretch technical textures, small decorative sprites or UI panels into rooms. Prefer coherent full-frame environment/layer families. Unity owns Cover/framing; ChatGPT owns choosing the correct environment.

============================================================
2D CINEMATIC LANGUAGE
============================================================

STARWARS_DELTA uses flat 2D visual assets. Do not make them pretend to be 3D through arbitrary perspective rotation, fake Y-axis orbit or decorative camera movement.

Prefer:
- cuts and cut-based reframing
- Close / Medium / Wide / ExtremeWide variation
- real inserts when the asset exists
- scale contrast within semantic baselines
- foreground / midground / background staging
- parallax using coherent layers
- screen direction and entrances/exits
- reaction shots
- monitor communication
- side-view action when side-view assets exist
- semantic Push/Pull only when revealing scale or changing attention

If camera purpose is unclear, use HOLD.

Useful coverage structures include:
DETAIL -> RELATIONSHIP -> WORLD
ACTION -> IMPACT -> REACTION
THREAT REVEAL
MONITOR COMMUNICATION
LAUNCH SEQUENCE
FACE-OFF WITH DEPTH
PULLBACK SCALE REVEAL
SHIP FLYBY
COMMAND ROOM ESCALATION

Do not default narrative shots to equal mechanical durations. Timing follows dramatic purpose.

============================================================
PROJECTILES, IMPACTS AND VFX
============================================================

A cutscene projectile may be staged without gameplay simulation:
actual CURRENT projectile sprite -> explicit Move -> reaches target -> exact CURRENT impact/explosion activates -> optional supported ScreenFlash/ImpactShake -> reaction animation/action.

This is valid cinematic staging. If the preferred ParticleSystem is not Catalog-exposed, an exact existing explosion sprite/effect may be used as an explicit placeholder. Never invent the explosion visual.

Effects need timing, purpose, depth/target when supported, readable occupancy and bounded lifetime. Procedural effects may omit assetId only when the CURRENT contract explicitly defines them as procedural.

============================================================
FILM AND JSON NO-ERROR PREFLIGHT - REQUIRED BEFORE DELIVERY
============================================================

Do not deliver knowingly blocked JSON and make the designer discover the obvious validator error inside Unity.

Before final JSON verify:
1. OPEN_CURRENT status is CURRENT_VERIFIED_OPEN and atomic identity matches the contract/Director.
2. JSON parses and uses exact CURRENT schema/closed-enum spellings.
3. Technical IDs are globally unique across actions, transitions, events, audio, dialogue and other stable identifiers.
4. Every cast Actor is legal canonical Actor identity; distinct named Persons do not collapse to one preferred identity unless intentional.
5. Every field uses the correct destination capability/primary use.
6. Every principal visual has inspected pixel evidence when visual fidelity is claimed.
7. Production storyboard principal identities match JSON identities; otherwise flag V3_STORYBOARD_JSON_ASSET_MISMATCH.
8. Every PlayAnimation exact ID is in that Actor's CURRENT compatibleAnimationIds.
9. Dialogue presentation/presentationMode/single-visual-source/locked-dialogue invariants hold.
10. Backgrounds are real environments for the intended location and are delegated to Unity Cover/framing rather than extreme authored scale.
11. No generated-root artifact or generated concept image is used as an authoring source.
12. No unsupported fake 3D rotation/view-angle trick is used to repair a missing visual.
13. Effects/projectiles have legal route, timing, target/purpose and bounded lifetime.
14. Shot scale/framing is not monotonous; screen direction and continuity are intentional.
15. Sequence/shot/action/UI/VFX timing stays inside owner intervals; ShowUi/HideUi ownership is valid.
16. System-managed authored scale stays near semantic baseline, normally 1.0.
17. Storyboard-to-JSON shot fidelity is checked: location, principal subject, world-vs-UI interpretation, framing, action direction, lifetime, depth, dialogue mode and major VFX beat.
18. Expected REAL BLOCKERS = 0 before delivery.

Yellow optional metadata/review notes are not the same as red blockers. Reduce avoidable auto-repair/warning noise, but do not destroy a good composition merely to eliminate harmless review notes.

============================================================
PREVIEW ACCEPTANCE
============================================================

A Timeline that plays is not automatically a successful film.

Treat as RED visual evidence: repeated effectively identical frames across unrelated shots; wrong location; giant/clipped principal actors; postage-stamp backgrounds/black borders; required portrait missing; floating portrait over grounded action when not intended; unintended occlusion; stale identity substitution; old actors leaking into later locations; principal diagnostic placeholder; effect with no target/depth relationship.

If JSON validation passes but cinematic realization is wrong, capture it as runtime/materialization failure evidence. Do not randomly rewrite asset IDs to hide infrastructure failure.

Never claim Unity visual success unless actual CURRENT Atlas pixels and resulting Unity output were compared.
