============================================================
AUTHORING ID SEMANTICS - HARD RULE
============================================================

AUTHORING_ASSET_ID_ONLY_FOR_RUNTIME_FIELDS
Director projections expose several identifier types. They are deliberately different and ARE NOT INTERCHANGEABLE.

VISUAL / EVIDENCE IDENTIFIERS:
- visualReferenceId
- Atlas page / Atlas slot
These exist for visual lookup/provenance. Never serialize them as runtime asset IDs.

SOURCE / MEMBERSHIP IDENTIFIERS:
- catalogAssetIds
- sourceRecordIds
These prove source membership/provenance. Their presence inside a Ui/Layer/Effect/Actor projection does NOT grant that exact member ID the projection's resolved runtime capability. Never copy one into JSON merely because it appears in the projection.

RUNTIME AUTHORING IDENTIFIERS:
- authoringAssetId = resolved runtime authoring ID for direct asset-bearing fields of that Director projection.
- canonicalActorAssetId / preferred Actor identity = persistent world/cast identity when CURRENT provides it.
- compatibleAnimationIds = exact legal Animation IDs for the exact Actor.
- compatibleDialogueVisualIds / exported dialogue tuples = exact legal dialogue mappings according to the dialogue contract.

FIELD-SPECIFIC SERIALIZATION RULES:
- ShowUi.assetId -> exact Ui projection authoringAssetId that itself resolves with Cutscene.UI.
- Layer/background asset field -> exact Layer projection authoringAssetId with the required Layer capability/use.
- Asset-backed Effect asset field -> exact Effect projection authoringAssetId with the required Effect capability/use.
- Audio asset field -> exact Audio projection authoringAssetId or exact contract-approved Audio authoring ID.
- cast[].visualAssetId -> canonical/preferred Actor identity when supplied; otherwise exact legal Actor authoring identity from CURRENT.
- PlayAnimation.animationAssetId -> exact member of that cast Actor's compatibleAnimationIds.
- Dialogue portrait/body/preset IDs -> exact compatible dialogue mapping required by the selected presentation contract; never guessed by family resemblance.

CRITICAL CAPABILITY RULE:
Capability is validated on the EXACT SERIALIZED RUNTIME ID, not on the parent Director projection that happens to contain it.

Therefore:
NEVER assume `ID appears inside a Ui projection` means `that ID is legal for ShowUi`.
NEVER assume `ID appears inside a Layer projection` means `that ID is legal for Layer materialization`.
NEVER assume `ID appears inside an Effect projection` means `that ID is legal for Effect materialization`.
NEVER assume source membership equals authoring permission.

Before final JSON, reverse-check every serialized asset ID against the field that owns it. The test is not merely `does this ID exist in CURRENT?`; the test is `is this exact ID the CURRENT authoring/canonical/compatible ID required by this exact field?`

SOURCE_RECORD_LEAKAGE_DIAGNOSTIC
If Unity reports `The catalog record does not have required capability ...` while the surrounding Director projection looked legal, first suspect that a catalogAssetId/sourceRecordId member leaked into JSON instead of the projection's authoringAssetId/canonical/compatible ID. Re-resolve the field from CURRENT Director. Do not randomly substitute another family member.

This exact class of bug is a RED preflight failure and must be fixed before delivery.

============================================================
STORY CLAIM MUST HAVE VISUAL PROOF - HARD INVARIANT
============================================================

Every major non-verbal story claim must be provable by the serialized visible result.

`intention`, sequence names, shot names, comments, metadata and dialogue describing an off-screen physical event do NOT implement that event.

For every major story beat, identify:
- the visible subject(s);
- the visible state before;
- the serialized action/change;
- the visible consequence/reaction;
- the shot(s) in which Unity will show that evidence.

Ask:
WHAT EXACTLY WILL UNITY DISPLAY THAT PROVES THIS CLAIM HAPPENED?

If the answer refers only to intention text, narration, dialogue, metadata, or an unseen event, the beat is not visually implemented.

Dialogue may count as implementation only when the beat itself is communication, speech, an order, a report or another inherently verbal event. Dialogue saying that a separate physical event occurred does not visually implement that physical event.

Examples:
- "ships arrive" requires ships/grouped fleet visuals that visibly enter, reveal, activate or move into frame;
- "pilot destroys ships" requires visible attacker/target relation, attack/projectile or equivalent action, impact, target reaction and changed target state;
- "enemy force disappears" requires the previously visible enemies to exit, deactivate, disappear, retreat or be destroyed;
- "the city falls into shadow" requires the city/location plus a visibly motivated occluding threat and a staged lighting/darkening change;
- "we won" may be communicated verbally, but a claimed physical victory over a visible enemy still requires the enemy state to visibly change.

============================================================
COMPOUND STORY EVENTS REQUIRE COMPOUND VISUAL EVIDENCE
============================================================

Do not use one semantically unrelated object as a symbolic substitute for a plural or compound event.

A fleet, crowd, battle, evacuation, launch wave, celebration or command-room escalation must be represented by visual evidence whose actual pixels and authored actions communicate that compound event.

This may be:
- multiple legal instances/actions;
- multiple coordinated Actors/Layers/Effects;
- or one exact CURRENT grouped asset whose inspected pixels already contain the required plurality/event and whose runtime destination is legal.

One ordinary ship does not become "a fleet" because `intention` calls it a fleet.
One explosion does not become "a battle".
One character does not become "a crowd".

Search CURRENT for the actual components or grouped visual needed to stage the event. Plural story language creates a quantity obligation. If the request says "many", "fleet", "dozens", "squadron", "crowd" or "wave", decide how that plurality will actually appear. If CURRENT cannot honestly show the requested quantity, change/reframe the composition or report an Asset/Capability Gap. Never silently collapse plurality into one convenient ordinary asset.

When a plural/grouped CURRENT visual already contains the required plurality in its actual pixels, one serialized asset may legitimately represent the group. The decision is based on observed pixels plus legal runtime role, not on the asset name alone.

============================================================
COMPOSITE CHARACTER AND KIT CONTRACT
============================================================

Never assume that a Head, Body, Weapon, Engine, Shield, accessory, Controls, Screen, VFX piece or other component asset can independently stand in for the complete object or character.

When CURRENT exposes a visual family as separate components, first determine whether Director/Contract defines:
- a canonical composite identity;
- an allowed component pairing;
- a presentation/composition contract;
- or independent legal authoring routes for those components.

Do not arbitrarily combine visually compatible parts. Source-folder proximity, matching names and matching art style are evidence for search only, not proof of runtime assembly compatibility.

For character kits, preserve one coherent identity across head/body/presentation components. A Head asset is not automatically a world Actor identity, and a Body asset is not automatically a complete character. Do not infer that `Koda Head` pairs with `Koda Body` merely because the names match unless CURRENT proves the relation and authoring route.

If CURRENT provides a canonical complete Actor/prefab, prefer it for world identity. If CURRENT provides a supported modular character/dialogue composition, keep cast identity separate from the presentation parts and serialize only the exact field-appropriate IDs required by that contract.

Ship and object kits follow the same rule. Base / Engine Effect / Shield / Weapons pieces may be combined only through a CURRENT-supported kit/composite route or through independent legal destinations whose composition is explicitly authored and visually coherent. Kit membership never grants capability by itself.

If the required composite cannot be authored through a CURRENT-supported route, change the composition or report an Asset/Capability Gap. Do not invent a composition system in JSON.

============================================================
STORY BEAT EVIDENCE PREFLIGHT - MANDATORY BEFORE SERIALIZATION
============================================================

Before JSON delivery, enumerate every major story beat and map it to its serialized visual evidence.

For each major beat record internally:
STORY CLAIM -> SHOT -> VISIBLE ELEMENTS -> ACTION/CHANGE -> CONSEQUENCE -> EXIT/FINAL STATE

Examples:

`many enemy ships arrive`
-> visible grouped fleet asset OR multiple legal enemy ship instances
-> staggered entrances/depth/positions or another visibly readable arrival
-> fleet remains visibly present in the resulting state.

`pilot destroys enemy ships`
-> attacker visible
-> projectile/motion/attack action
-> target visible
-> impact
-> target reaction/destruction/exit.

`enemy force disappears`
-> previously visible enemy elements
-> explicit exits/removals/deactivation/destruction
-> subsequent shot visibly lacks them.

`everyone believes they won`
-> observable relaxation/celebration/dialogue/reaction using legal CURRENT presentations.

`giant ships eclipse Earth`
-> Earth/location visibly established
-> giant ship visual enters/reveals at readable relative scale
-> legal darkening/occlusion/change is visibly staged
-> later frame visibly communicates overwhelming scale.

If a major non-verbal claim has no corresponding serialized visible evidence, preflight fails even when schema validation passes.

Long duration creates a content obligation, not permission to pad time. Do not reach 240/300/3000 seconds by cloning one validated sequence, alternating static visual/dialogue blocks, or holding an unchanged frame for mechanical convenience. Reuse is allowed only when each reused beat creates a deliberate new story state, composition, action, timing or consequence.

For every substantial sequence, the internal shot-realization plan should identify:
1. dramatic beat;
2. physical location/viewpoint;
3. visible principal elements AND visible count/grouping;
4. start state;
5. explicit movement/action/state change;
6. camera purpose and framing;
7. dialogue/reaction presentation if any;
8. VFX/audio beat if any;
9. end state / what persists into the next shot;
10. on-screen evidence proving the story beat.

Then map that plan to exact CURRENT assets and legal JSON actions. Do not work backward from a previously-valid JSON template and merely rewrite intentions until the template sounds like a different movie.

============================================================
PREVIEW ACCEPTANCE
============================================================

A Timeline that plays is not proof that the movie succeeded.

RED visual evidence includes:
- effectively identical frames across unrelated shots
- wrong location or missing location transition
- giant/clipped principal actor
- postage-stamp background / black borders
- required portrait missing
- floating portrait over grounded action when not intended
- unintended occlusion
- stale/wrong identity substitution
- old actors leaking into later locations
- principal diagnostic placeholder
- effect with no target/depth relationship
- runtime result that materially disagrees with the approved exact-asset storyboard
- a story claim of fleet/crowd/wave/many objects represented by one ordinary object whose pixels do not actually depict the claimed plurality
- destruction/retreat/arrival described in text while the visible target/object state does not actually change
- a giant-threat/shadow reveal described in intention but realized only as generic brightness/background change without the visible cause
