AUTHORING RULES - READ BEFORE USING ANY RECORD
DEVORA NORMAL FRONTEND: DEVORA / ChatGPT authors CUTSCENE_SCRIPT_V1. The Simple Adapter resolves CURRENT handles/routes and compiles through existing V3 into V5. V5 is backend, not the normal NEW authoring format.
CAMERA FIRST: camera framing -> screenX/screenY -> screenWidthFraction/screenHeightFraction -> real Renderer bounds -> Unity scale.
DIALOGUE NEAR/FAR: in normal locked two-person portrait dialogue the active speaker is NEAR/larger and the listener is FAR/smaller; speaker change reverses dominance without changing identity.
STORY EVIDENCE: physical claims require visible serialized evidence; dialogue text alone does not prove an unseen physical event.
This package is self-contained. No external Catalog knowledge is required.
NORMAL NEW AUTHORING: return one complete CUTSCENE_SCRIPT_V1 JSON object. DEVORA owns story, semantic handles, visible evidence, dialogue intent and camera-first screen composition; Unity owns exact runtime IDs, CURRENT fingerprints, route resolution and final V5 serialization.
SIMPLE HANDLE SAFETY: normal NEW authoring uses exact semantic handles from matching CURRENT truth. Never invent a handle or silently substitute a related identity. Unity resolves the handle to exact backend assets.
SIMPLE AUTHORING DOES NOT CREATE BACKEND TECHNICAL IDS. Unity generates globally unique V5 action/transition/event/audio/line IDs during Simple -> V3 -> V5 compilation.
PLACEMENT: cutscenePrimaryUse is authoritative. Layer-primary records are layers/backgrounds, Actor-primary records are cast/world actors, Ui-primary records are dialogue/UI presentation, Animation-primary records are animation references, Effect-primary records are effects, and Audio-primary records are audio.
ACTOR PRESENTATION: set cast[].presentationMode exactly to WorldActor, DialoguePortrait, or Both. Both permits world-action and portrait shots only when their active intervals do not overlap. An omitted presentationMode uses legacy spawnWorldActor as WorldActor/DialoguePortrait; it never infers Both.
ANIMATION: PlayAnimation is legal only when the exact animationAssetId appears in that actor record's compatibleAnimationIds. Never infer compatibility from names, folders, packs or visual similarity. If the list is empty, use another legal non-animation action.
DIALOGUE: normally show only speaker + listener and rotate pairs for larger conversations. Use current canonical layout enums. If any line in a shot has stage.lockStaging=true, that shot's actorActions must be empty: no Hold, Move, Enter, Exit or PlayAnimation.
PREFER SIMPLE COMPOSITIONS: use the fewest fragile dependencies that tell the story. Preview-safe records may produce yellow review notes even when not publish-safe; simplify or omit optional elements instead of inventing unsupported data.
Return canonical enum spellings only. Do not copy an example when it conflicts with these rules; these rules are authoritative.
SEMANTIC FIREWALL: descriptive semantic language is not automatically legal V5 vocabulary. Creative intent flows through semantic IR, explicit CURRENT mapping and canonical validation before serialization. Never assign a semantic string directly to a closed V5 field.
BAD: { role: RemoteOfficer, listenerEmotion: Neutral }
GOOD: { role: SupportingCharacter, entityKind: Person, entitySubKind: RemoteOfficer, listenerEmotion: Serious }
STRUCTURED CREATIVE INTENT: creativeIntent is always an object with summary, style and mood string fields. Never serialize creativeIntent as a plain string.
CLOSED-FIELD GUARDRAILS: never put a story job, rank, species, ship class or beat label into a structural enum field.
- cast[].role is only Hero, SupportingCharacter, Antagonist, Prop, Environment or Ui. Commander/Pilot/RemoteOfficer/RemoteAnalyst are SupportingCharacter; EnemyCommander/Villain/Boss are Antagonist. Keep the specific narrative label in entitySubKind or intention.
- shotType is camera grammar only: Establishing, CloseUp, Medium, Wide, ExtremeCloseUp, TwoShot, OverTheShoulder, Reaction, Insert, Reveal, Tracking, Follow or Static. Put Launch/Chase/Threat/Counterattack and other beat names in intention; choose shotType from framing and camera behavior.
- layer role uses Midground, never MidBackground. Dialogue emotion and expression are separate closed vocabularies: Serious is an emotion; Determined/Concerned/Urgent/Relieved are expressions.
FINAL CLOSED-FIELD CHECK: before returning JSON, compare every closed value with CONTRACT/CUTSCENE_ENUMS_V5.json. Never serialize an import alias even when Unity can recover it for Editable Preview.

CINEMATIC MULTI-PLANE COMPOSITION
For Establishing, Exterior, Action or Reveal beats, prefer a coherent multi-plane composition when materially useful Catalog planes exist; aim for roughly three useful planes rather than an arbitrary count.
Use FarBackground, Background, Midground, Foreground and Layer-primary Atmosphere roles when supported by reviewed metadata. Prefer one coherent familyId/collection and mix only when compatible planes are genuinely missing.
Space, planet and interior examples may use distant world/sky, readable set, actor-supporting midground and restrained foreground framing or haze. Do not flatten every Layer-primary record to Background.
The destination field remains authoritative: sequence.layers and shot.layerActions require Layer-primary records even when role is Overlay or Ui; dedicated dialogue/UI fields require Ui-primary records.
Layer-role Atmosphere is legal only in a Layer field. stage.atmosphereVfxAssetIds always resolve to Effect-primary records; smoke, fire and other Effect-primary VFX do not belong in sequence.layers.
FarBackground and Background use sortingOrder < 0. For Move/Parallax, parallaxFactor multiplies authored displacement (0=no displacement, 1=full delta); Scroll uses scrollUnitsPerSecond. Distant planes generally move less than nearer planes.
Locked dialogue remains line/stage-driven with one explicit stage.backgroundAssetId plus presentation assets and optional Effect-primary atmosphere VFX. With lockStaging=true, actorActions and moving parallax are not authored in that dialogue beat.
Give each shot one dominant intention, use compositionTargetId for the focal entity, choose one dominant base camera action, and use HardCut only for a genuine framing reset. Shake, ImpactShake and Recoil support the beat additively.

DIALOGUE PRESENTATION RULES
- cast[] is identity only; it never creates a world actor by itself.
- Set cast[].presentationMode=WorldActor for world-only, DialoguePortrait for portrait-only, or Both for an explicitly authored actor used in both isolated routes.
- Set useGameplayObject=true for the gameplay-object route; it never creates a generated clone.
- Dialogue visuals are line/stage-driven. Use exactly one portrait or body source per visible participant; an explicit body is authoritative and suppresses portrait fallback.
- Portrait, body, head and speech-bubble assets are Ui dialogue presentation; they do not create world actors.
- Standard dialogue has one speaker and one listener, with one visible background.
- Rotate speaker/listener pairs for 3+ character conversations; do not add a third visible participant.
- If you select a Ui-primary DialogueBubble / SpeechBalloon asset, put its exact assetId in $.sequences[].shots[].dialogue[].dialogueFrameAssetId. Do not invent dialogueBubbleAssetId.
- stage.uiForm at $.sequences[].shots[].dialogue[].stage.uiForm is the existing presentation-layout field; it does not create a second bubble asset field.
- When any dialogue line in a shot has stage.lockStaging=true, the owning shot.actorActions MUST be empty. Do not use Hold, FreezePose, Enter, Exit, Move, PlayAnimation, or any other world-actor action to keep a dialogue actor static. Dialogue visuals are controlled by the dialogue presentation fields only; place world-actor activity in a separate action shot before or after the locked dialogue shot.
- Use HardCut between framing changes. Never silently fall back to SUBTITLE_ONLY.
- Full preset/layout/grammar/camera semantics are in CUTSCENE_AUTHORING_CONTRACT.json. For new authoring, choose one exact compatibleTuples entry for the selected presentationPreset; do not mix the three independent lists by guesswork.
- Speech balloons are optional. Use one only when an exact Preview-safe Ui-primary balloon exists, its tail matches the visual speaker position, and the selected presentation supports that route.
- Left speaker -> prefer an explicit LeftSpeaker / TailLeft variant; right speaker -> RightSpeaker / TailRight; center or monologue -> CenterSpeaker / TailDown where appropriate.
- Do not invent NearSpeaker, FarSpeaker, RadioSpeech, ThoughtBubble or ShoutBubble semantics. If no appropriate explicit balloon exists, use the canonical Dialogue Stage frame/presentation.

SPATIAL COMPOSITION
Unity owns routine frame fitting: Background/FarBackground layers are Cover-fit to the generated camera, actors receive bounded semantic base sizing, and ordinary generated UI gets screen-space placement defaults. Do not compensate for source texture size by inventing extreme x/y/scale values.
Do not author defensive cleanup merely to stop generated content at its owner boundary: sequence-owned content ends with the sequence and shot-local content ends with the shot. Use explicit Exit/Deactivate when the story needs an earlier disappearance or an explicit hide/re-entry beat.

DIALOGUE EMOTION VS EXPRESSION
stage.speakerEmotion, stage.listenerEmotion and delivery.emotion use only: Serious, Shock, Anger, Perplexed, Sad, Happy.
delivery.pace uses only CURRENT values Slow, Medium or Fast. Semantic Slow/Measured/Conversational/Natural/Hesitant/Rapid/Urgent values are mapped before serialization.
Use speakerExpression/listenerExpression/reaction.expression for acting choices such as Determined, Concerned, Shocked or Relieved. Do not put those expression words into emotion fields.

ACTOR IDENTITY AND PROPORTIONS
- When an Actor record exports preferredActorAssetId, use that exact preferred record for cast[].visualAssetId unless the story explicitly requires a different identity state. Do not use Run/Death/Hit/Jump/mid-animation frames as the persistent cast identity merely because the action name matches.
- For dialogue, speakerPortraitAssetId/listenerPortraitAssetId must come from that Actor record's compatibleDialogueVisualIds when the list is non-empty. Never borrow a portrait from another character because it looks plausible. An explicit stage body wins over a portrait and prevents portrait fallback; with no body, repair may select a same-identity portrait or use the selected preset's allowsBuiltInParticipantFallback only when exported as true. Otherwise choose another exact compatible tuple/preset. Automatic repair never silently changes the story to SUBTITLE_ONLY.
- Distinct named Person cast members require distinct preferred Actor identities unless they intentionally represent the same narrative identity/clone. Do not manufacture Pilot/Commander as two frames of the same character family.
- Layer-only rocks/meteorites are not cast actors. Use Layer Move/Parallax for scenery/debris, or choose an Actor-primary movable asset when independent Actor actions are required.
- cutsceneSystemManagedProportions=true means Unity owns ordinary visual scale. Author scaleX/scaleY near 1.0 as a hint only; do not hand-tune different source pixel sizes into fake world proportions. Use cutsceneProportionClass, cutsceneScaleBasis and cutsceneTargetScreenFraction as the semantic baseline.
- Human/robot/ship/fighter/large-ship proportions are relative screen composition classes, not real-world meters. A fighter should not be human-sized, a robot should not accidentally fill the frame, and a rescue/capital ship should not inherit the same raw scale as a small fighter.

ANIMATION SAFETY
PlayAnimation is legal only when the exact animationAssetId appears in the exact Actor record's compatibleAnimationIds.
Never infer compatibility from folder, filename, common prefix, package name, actor name or visual similarity.
VERIFIED COMPATIBLE ANIMATIONS: when compatibleAnimationOptions are supplied, use their exact assetId and prefer the matching verified Run, Walk, Hit or Idle animation when the requested action clearly asks for it.
Move controls world movement; PlayAnimation controls visual character animation. A running person normally uses PlayAnimation(Run) plus Move(...). If no verified Run exists, use Move without PlayAnimation and keep Preview working.
If compatibleAnimationIds is empty, do not author PlayAnimation for that actor; use another legal action.
