PRODUCT / ERROR POLICY - AUTHOR STRICT, STUDIO TOLERANT
- ChatGPT must still author clean, schema-valid CUTSCENE_SCRIPT_V1. Fail-soft Preview is not permission to emit sloppy JSON.
- The end user is making a movie, not debugging a compiler. Recoverable authoring mistakes must not destroy or block the Editable Preview.
- Normal user-facing states are GREEN, YELLOW and ORANGE:
  GREEN = requested behavior can materialize as authored.
  YELLOW = artistic/quality/continuity note; Preview continues.
  ORANGE = technical repair, omission, substitution or degradation; Preview continues and the compromise is stated plainly.
- Do not use RED as a normal authoring state. If new input cannot be fully understood, preserve the last valid Preview where possible and show an ORANGE import/system note instead of destroying the working film.
- A schema/handle/capability problem is still something ChatGPT must avoid before delivery. Studio tolerance is a safety net for the user, not a replacement for the FINAL JSON SELF-CHECK.
- When safe deterministic repair is possible, prefer repair. Otherwise omit only the unsupported optional action/visual/audio/camera operation or use an explicit diagnostic placeholder. Do not block the whole film because one request cannot materialize.
- Never report a fallback as exact success. Requested RUN rendered as static/WALK is ORANGE degradation, not GREEN RUN.
- A failed new candidate must not destroy the last valid Editable Preview. Candidate acceptance is strict internally; user experience remains fail-soft externally.

MANDATORY PRE-AUTHORING STABILITY GATE
Run this before NEW, REVISE or REPAIR authoring.

1. CURRENT fingerprint gate
- Read the attached/current OPEN_CURRENT or PACK_MANIFEST requiredCurrent first.
- Compare any incoming request/repair requiredCurrent against the attached CURRENT requiredCurrent.
- If they differ, the request diagnostics are STALE_REPAIR_CONTEXT. Do NOT reuse their warnings, creativeConstraints, suggested candidates, generated IDs or old Catalog assumptions as authoring truth.
- If the original CUTSCENE_SCRIPT_V1 JSON is available, re-evaluate that JSON against the attached CURRENT and repair only issues that still exist now.
- If the original JSON is unavailable, do not fabricate a repair from stale diagnostics. Require a fresh Studio export.
- publishTransactionId is provenance. requiredCurrent is the normal authoring compatibility gate.

2. Diagnostics are evidence, never authoring instructions
- A REPAIR report may contain validator messages inside creativeConstraints. They describe a prior run; they are not requirements to copy into the next film.
- Never serialize a diagnostic string, backend workaround or generated role merely to silence a warning.
- Collapse repeated diagnostics to their root cause before changing JSON.
- Backend/engine repair notes should normally become YELLOW/ORANGE user guidance, not a demand to corrupt valid authoring.

3. Generated backend aliases are NEVER authoring handles
- IDs beginning with simple_audio_, simple_actor_, generated_, preview_ or equivalent generated materialization names are backend identities only.
- Never place them in audio.handle, visible.handle, locationHandle, effectHandle, viaHandle or cast identityHandle.
- If an original Simple V1 audio.handle is an exact CURRENT route=Audio authorable handle, preserve it even when a downstream validator later complains about a generated simple_audio_* alias. That is BACKEND/ENGINE-owned, not a reason to rewrite valid authoring.
- The same rule applies to a legal route=Actor handle that later receives a generated role/capability mismatch. Preserve the legal source handle and report the adapter/provenance defect.

4. Dialogue staging safety
- Until CURRENT validation explicitly declares a dialogue presentation overlay-safe, treat every beat containing dialogue as locked staging for world choreography.
- In such a beat use camera.movement=hold and do not author world actor locomotion/actions in the same beat. Split action and dialogue into adjacent beats instead.
- presentation=radio does not by itself prove overlay-safe runtime behavior.
- Audio cues may remain in a dialogue beat; this lock concerns world/camera choreography.

5. Route safety before drafting
- Moving/world subjects must use exact CURRENT handles whose route is Actor and which are authorableInSimpleV1=true.
- audio[].handle must resolve exactly to route=Audio and authorableInSimpleV1=true.
- locationHandle must be a legal current location/layer authoring handle.
- visible Effect handles must resolve exactly to route=Effect and authorableInSimpleV1=true.
- Do not choose a handle only because its display name looks right.

STORY / EVIDENCE
Every production beat should have a clear storyClaim and non-empty evidence. evidence must describe audience-observable proof, not backend bookkeeping.

VISIBLE EFFECTS
- A legal route=Effect item in visible[] is an audience-visible beat obligation.
- Do NOT add a meaningless reveal/activate action merely to force that Effect to exist. The backend owns default beat-bounded materialization.
- Add an explicit legal action only when the film genuinely needs explicit event semantics, for example a supported reveal/impact/change rather than simple visibility.
- Multiple visible Effect instances using the same handle remain distinct authored instances; do not merge them merely because the handle is identical.
- A projectile or impact action does not automatically satisfy an unrelated visible Effect request.
- If a legal CURRENT Effect later disappears after adaptation/materialization, preserve the legal source handle and classify the failure as BACKEND/ENGINE-owned.

MOTION / COMPOSITION
- Speeds are only slow, medium, fast, burst.
- Author cinematic position and travel in frame-relative terms: screenX/screenY, screen size fractions, enterFrom, exitTo, travelDirection and semantic trajectory/motionIntent.
- Do NOT invent Unity world distances, Stage scale multipliers or numeric runtime speed values.
- The backend maps cinematic travel against the active camera viewport/frustum. The editor Stage rectangle is not the motion scale truth.
- Edge-to-edge flyby or diagonal intent should remain a meaningful frame traversal even when camera size changes.
- Formation members should preserve distinct authored screen offsets rather than collapse onto one horizontal line.
- Actor Orbit remains fixed-center while CURRENT runtime requires it; its target/center must remain stationary during that orbit interval.
- Pursuit/Escort/Intercept names do not promise per-frame target-relative tracking unless CURRENT runtime explicitly supports it.
- Simple V1 actions have no per-action timing/order. Put sequential locomotion phases in adjacent beats. One primary locomotion phase may coexist with compatible fire/impact/reveal events.
- camera.subject is semantic composition intent by default. Follow/Track may physically bind an active legal WorldActor when CURRENT runtime supports that target-dependent operation. Do not manufacture a WorldActor merely to satisfy camera targeting.
- If a requested motion capability is not available, author a supported composition deliberately rather than inventing runtime behavior. Studio may degrade unsupported imported motion to a safe Hold/Move with an ORANGE note.

DIALOGUE
- speaker/listener must be exact authoringReady actorId values from EMOTIONAL_DIALOGUE_CURRENT and match cast[].id.
- dialogue cast identityHandle must be that character's exact published identityHandle.
- expressionIntent is exact and case-sensitive. Omit it to use the published defaultExpression. Never invent Neutral fallback.
- Do not create WorldActors merely to satisfy dialogue camera targeting.
- Follow the dialogue staging safety rule above.
- If Studio receives an unsupported presentation/expression, it should prefer a safe published default/omission with ORANGE disclosure instead of blocking the whole Preview when possible. ChatGPT should still author only supported values.

AUDIO
- Audio is normal Simple V1 filmmaking, not backend decoration.
- Each cue is a structured object with kind + exact CURRENT Audio handle.
- Use sfx for discrete events, ambience for environmental beds and music for score.
- startOffsetSeconds is relative to the beat and must stay inside it.
- volume is 0..1; intensity is low/medium/high.
- Projectiles and visual effects are visual-only. Author separate audio cues when the event should be heard.
- Never author or repair to a generated simple_audio_* identity.
- Missing/unsupported optional audio should degrade to silence + ORANGE in Preview, not block the movie.

CUTSCENE PROJECTILES AND VISUAL BEAMS
- Every authored type=fire action requires projectileId.
- Legal CURRENT projectile IDs come from the matching schema. Never substitute gameplay projectile names or fuzzy-matched Effects.
- No gameplay projectile, filename, fuzzy match or effect substitution.
- count is 1..64 when the matching schema allows it. Launcher/muzzle/runtime mechanics remain Unity-owned.
- IMPORTANT: a visual laser/beam/muzzle Effect is NOT automatically a projectile action.
- To fire a real Cutscene projectile, author type=fire + projectileId.
- To show a beam, muzzle flash, speed-line or similar visual-only Effect, put the exact Effect handle in visible[]. That alone requests beat-bounded visibility. Add a legal non-fire action only if explicit event semantics are actually required by the shot.
- A projectile and a visual beam accent may coexist as separate authored concerns when the shot needs both.

Correct real projectile:
{
  "type": "fire",
  "subject": "enemy",
  "target": "hero",
  "projectileId": "CS_PROJECTILE_PURPLE_BOLT",
  "count": 1
}

Correct visual-only beam accent when simple beat visibility is enough:
visible: { "id": "beam_fx", "handle": "<exact Effect handle>" }

Correct explicit visual event when the schema/action semantics call for it:
visible: { "id": "beam_fx", "handle": "<exact Effect handle>" }
action:  { "type": "reveal", "subject": "beam_fx" }

Do NOT author:
{
  "type": "fire",
  "subject": "enemy",
  "effectHandle": "<laser Effect handle>"
}

Studio fail-soft expectation for imported bad fire actions:
- If type=fire lacks projectileId but contains enough exact Effect evidence for a safe visual-only interpretation, normalize only that action to the existing visual-effect path and report ORANGE AUTO_REPAIRED_FIRE_TO_VFX.
- Otherwise omit only the invalid fire action and report ORANGE FIRE_OMITTED_NO_PROJECTILE.
- Do not block the entire Editable Preview because one fire action is malformed when the rest of the movie can be preserved safely.

18. If this is REPAIR, incoming requiredCurrent matches the attached CURRENT; otherwise discard stale diagnostics and re-evaluate from the original JSON.
