CLOSED-WORLD AUTHORING - MANDATORY
============================================================

Use only assets, IDs, capabilities, compatibility mappings and visual evidence that exist in the CURRENT STARWARS_DELTA publish resolved from OPEN_CURRENT.json.

1. Never invent, approximate, substitute, hallucinate or remember an asset because it would make the scene nicer.
2. Never mix old Catalog IDs, old JSON IDs, old Instruction Books, old screenshots or another publish transaction into new authoring.

4. A Visual Atlas ID, screenshot ID, sourceRecordId, catalogAssetId or representative image is not automatically a runtime authoring ID.
5. For important elements preserve the chain: OBSERVED VISUAL -> DIRECTOR ENTRY -> CANONICAL/AUTHORING ID -> LEGAL ROLE/CAPABILITY.
6. If CURRENT lacks an optional ideal asset, finish with the best legal CURRENT composition. If an essential visual cannot be represented honestly, report one explicit Asset Gap instead of synthesizing it.

VISUAL ACCESS HONESTY - NON-NEGOTIABLE
============================================================

Metadata is search evidence, not visual inspection. displayName, tags, description, source path, asset ID, atlas page number, atlas slot, a PDF URL or binary access do not prove that the image was actually seen.

Required visual-verification chain:
OBSERVED PIXELS -> EXACT ATLAS PAGE/SLOT -> EXACT visualReferenceId -> EXACT DIRECTOR ENTRY -> EXACT CANONICAL/AUTHORING RUNTIME ID.

VISUAL_ATLAS_PDF_REQUIRED_FOR_PRODUCTION
For ANY production storyboard, cinematic asset selection, important shot design, visual QA plan, or claim that a shot represents the game, ChatGPT MUST inspect actual pixels from the CURRENT STARWARS_DELTA_CHATGPT_VISUAL_ATLAS_CURRENT.pdf.

The Visual Atlas PDF is the authoritative source for WHAT THE ASSET LOOKS LIKE.
The Director/Catalog/Contract are the authoritative sources for WHICH RUNTIME ID AND CAPABILITY MAY LEGALLY BE USED.
Both halves are mandatory.

A Director name, tag or description can narrow search candidates, but it can never replace looking at the PDF. Do not approve a principal ship, character, environment, robot, projectile, portrait, effect or UI visual from metadata alone.

Rendered page images are acceptable only when they are provably pages from the exact CURRENT Visual Atlas PDF/publish. A generated image, redrawn image, concept image, screenshot from an old publish or visually similar external image is not Atlas evidence.

For every principal visible asset selected for a production storyboard or important shot, ChatGPT must be able to recover:
- observed Atlas page and slot and/or visualReferenceId
- exact Director category entry
- exact runtime authoring/canonical ID used in JSON
- exact legal destination/capability of that field

Do not build a production storyboard first and inspect the PDF later. Pixel inspection happens BEFORE a visual is approved into the storyboard.

============================================================
AUTHORING ID SEMANTICS - HARD RULE
============================================================

AUTHORING_ASSET_ID_ONLY_FOR_RUNTIME_FIELDS
Director projections expose several identifier types. They are deliberately different and ARE NOT INTERCHANGEABLE.

VISUAL / EVIDENCE IDENTIFIERS:
- visualReferenceId
- Atlas page / Atlas slot
These exist for visual lookup/provenance. Never serialize them as runtime asset IDs.

SOURCE / MEMBERSHIP IDENTIFIERS:
- catalogAssetIds
- sourceRecordIds
These prove source membership/provenance. Their presence inside a Ui/Layer/Effect/Actor projection does NOT grant that exact member ID the projection's resolved runtime capability. Never copy one into JSON merely because it appears in the projection.

RUNTIME AUTHORING IDENTIFIERS:
- authoringAssetId = resolved runtime authoring ID for direct asset-bearing fields of that Director projection.
- canonicalActorAssetId / preferred Actor identity = persistent world/cast identity when CURRENT provides it.
- compatibleAnimationIds = exact legal Animation IDs for the exact Actor.
- compatibleDialogueVisualIds / exported dialogue tuples = exact legal dialogue mappings according to the dialogue contract.

FIELD-SPECIFIC SERIALIZATION RULES:
- ShowUi.assetId -> exact Ui projection authoringAssetId that itself resolves with Cutscene.UI.
- Layer/background asset field -> exact Layer projection authoringAssetId with the required Layer capability/use.
- Asset-backed Effect asset field -> exact Effect projection authoringAssetId with the required Effect capability/use.
- Audio asset field -> exact Audio projection authoringAssetId or exact contract-approved Audio authoring ID.
- cast[].visualAssetId -> canonical/preferred Actor identity when supplied; otherwise exact legal Actor authoring identity from CURRENT.
- PlayAnimation.animationAssetId -> exact member of that cast Actor's compatibleAnimationIds.
- Dialogue portrait/body/preset IDs -> exact compatible dialogue mapping required by the selected presentation contract; never guessed by family resemblance.

CRITICAL CAPABILITY RULE:
Capability is validated on the EXACT SERIALIZED RUNTIME ID, not on the parent Director projection that happens to contain it.

Therefore:
NEVER assume `ID appears inside a Ui projection` means `that ID is legal for ShowUi`.
NEVER assume `ID appears inside a Layer projection` means `that ID is legal for Layer materialization`.
NEVER assume `ID appears inside an Effect projection` means `that ID is legal for Effect materialization`.
NEVER assume source membership equals authoring permission.

Before final JSON, reverse-check every serialized asset ID against the field that owns it. The test is not merely `does this ID exist in CURRENT?`; the test is `is this exact ID the CURRENT authoring/canonical/compatible ID required by this exact field?`

SOURCE_RECORD_LEAKAGE_DIAGNOSTIC
If Unity reports `The catalog record does not have required capability ...` while the surrounding Director projection looked legal, first suspect that a catalogAssetId/sourceRecordId member leaked into JSON instead of the projection's authoringAssetId/canonical/compatible ID. Re-resolve the field from CURRENT Director. Do not randomly substitute another family member.

This exact class of bug is a RED preflight failure and must be fixed before delivery.

============================================================
ACTOR IDENTITY AND CAST
============================================================

Cast is identity. Animation/action frames do not manufacture new identities.

- cast[].visualAssetId must resolve to legal Actor-primary/canonical identity.
- Prefer canonicalActorAssetId/preferred Actor identity when CURRENT supplies it.
- Do not use Run/Hit/Death/Walk/Launch frames as persistent cast identity merely because they depict the desired pose.
- Distinct named Person characters require distinct resolved preferred Actor identities unless intentionally representing the same identity/clone.
- Do not create six differently named extras around one normalized Person identity. Use fewer distinct legal people or an explicit supported crowd/clone mechanism.
- World/cast identity and UI portrait identity are separate roles.

============================================================
ANIMATION COMPATIBILITY IS EXACT
============================================================

PlayAnimation is legal only when the exact animationAssetId appears in the exact selected Actor's CURRENT compatibleAnimationIds.

Never infer animation compatibility from filename, package, family name, appearance or semantic wording. If no exact compatible animation exists: choose another compatible animation, use a legal static/Move/Hold presentation, or report a gap.

For a running world character, use exact compatible PlayAnimation(Run) plus Move when both are legal. Move alone slides a mannequin. Run alone runs in place.

============================================================
DIALOGUE PRESENTATION INVARIANTS
============================================================

- Cast identity remains Actor-primary/canonical. Portrait/body/frame assets are presentation sources, not cast identity.
- Dialogue-only participants use presentationMode=DialoguePortrait and spawnWorldActor=false.
- presentationMode=Both is legal only when explicitly authored and world representation is temporally isolated from portrait representation. Never infer Both.
- FACE_TO_FACE_PORTRAITS participants cannot simultaneously remain active as world actors in the same locked-dialogue window.
- Each visible participant has one primary source: portrait XOR body, not both.
- SUBTITLE_ONLY carries no portrait/body participant visuals.
- Locked dialogue requires owning shot actorActions=[].
- Locked dialogue camera is Hold, supported Snap or supported cut-based presentation only. No continuous Push/Pull/Zoom/Pan/Follow/Track/Drift/Orbit merely for decoration.
- Portrait close-ups, speaker focus, two-shot and reaction cuts are valid 2D cinematic variety when legal Visual Atlas sources exist. Never invent a facial close-up not present in CURRENT Visual Atlas.

Preserve/obey current diagnostics including:
DIALOGUE_ACTOR_PRESENTATION_CONFLICT
DIALOGUE_VISUAL_SOURCE_CONFLICT
DIALOGUE_VISUAL_SOURCE_UNSUPPORTED
CUTSCENE_DIALOGUE_CAMERA_MOTION_FORBIDDEN

============================================================
DESTINATION CAPABILITY BEATS VISUAL RESEMBLANCE
============================================================

A picture that looks like UI is not automatically legal UI. A rock that looks movable is not automatically an Actor. A portrait-looking sprite is not automatically world cast.

- ShowUi requires exact Ui authoring ID with Cutscene.UI.
- Layer actions require exact Layer authoring legality.
- Asset-backed effects require exact Effect authoring legality.
- Animation fields require exact compatible Animation IDs.
- Audio fields require exact Audio authoring IDs.

Visual resemblance, shared source texture, matching filename or membership in the same projection is never sufficient proof of destination capability.

Prefer canonical direct authoring over auto-repair. Automatic repair is a safety net for legacy/bad input, not an authoring strategy for new ChatGPT output.

============================================================
SYSTEM-MANAGED PROPORTIONS AND BACKGROUNDS
============================================================

When systemManagedProportions=true, authored scaleX/scaleY defaults to 1.0. Unity owns semantic normalization. Do not enlarge a tiny source image by 8x because framing is broken. Wrong asset, wrong presentation, wrong camera coverage and wrong scale are separate problems.

Background/FarBackground assets must visually function as the intended location when inspected in the Visual Atlas. Do not stretch technical textures, tiny decorative sprites or UI panels into rooms. Prefer coherent full-frame environment/layer families. Unity owns Cover/framing; ChatGPT owns choosing the correct environment.

============================================================
2D CINEMATIC LANGUAGE
============================================================

STARWARS_DELTA uses flat 2D visual assets. Do not force them into fake 3D through arbitrary perspective rotation, fake Y-axis orbit or decorative camera gymnastics.

Prefer:
- cuts and cut-based reframing
- Close / Medium / Wide / ExtremeWide variation
- real inserts only when the exact asset exists
- semantic scale contrast within system baselines
- foreground / midground / background staging
- parallax using coherent real layers
- screen direction and entrances/exits
- reaction shots
- monitor communication
- side-view action when side-view assets exist
- semantic Push/Pull only when revealing scale or changing attention

If camera purpose is unclear, use HOLD.

Useful coverage patterns include:
DETAIL -> RELATIONSHIP -> WORLD
ACTION -> IMPACT -> REACTION
THREAT REVEAL
MONITOR COMMUNICATION
LAUNCH SEQUENCE
FACE-OFF WITH DEPTH
PULLBACK SCALE REVEAL
SHIP FLYBY
COMMAND ROOM ESCALATION

Do not default narrative shots to equal mechanical durations. Timing follows dramatic purpose.

============================================================
PROJECTILES, IMPACTS, VFX AND AUDIO
============================================================

A cinematic projectile may be staged without gameplay simulation:
exact CURRENT projectile visual -> explicit Move -> target -> exact CURRENT impact/explosion -> optional supported ScreenFlash/ImpactShake -> reaction.

If the preferred ParticleSystem is not Catalog-exposed, an exact existing explosion sprite/effect may be used as an explicit placeholder. Never invent an explosion visual.

Effects need legal route, purpose, timing, target/anchor when supported, semantic depth, readable occupancy and bounded lifetime. Procedural effects may omit assetId only when the CURRENT contract explicitly defines them as procedural.

Audio is first-class. Use exact CURRENT Audio records for ambience, engines, impacts, alerts/UI, music, voice/comms or intentional silence when appropriate. Audio is non-visual and must not be counted as a Visual Atlas coverage gap.

============================================================
PREVIEW ACCEPTANCE
============================================================

A Timeline that plays is not proof that the movie succeeded.

RED visual evidence includes:
- effectively identical frames across unrelated shots
- wrong location or missing location transition
- giant/clipped principal actor
- postage-stamp background / black borders
- required portrait missing
- floating portrait over grounded action when not intended
- unintended occlusion
- stale/wrong identity substitution
- old actors leaking into later locations
- principal diagnostic placeholder
- effect with no target/depth relationship
- runtime result that materially disagrees with the approved exact-asset storyboard

If JSON validation passes but cinematic realization is wrong, save/capture it as runtime/materialization failure evidence. Do not randomly rewrite asset IDs to conceal infrastructure failure.

Never claim Unity visual success unless actual CURRENT Visual Atlas pixels and resulting Unity output were compared.
