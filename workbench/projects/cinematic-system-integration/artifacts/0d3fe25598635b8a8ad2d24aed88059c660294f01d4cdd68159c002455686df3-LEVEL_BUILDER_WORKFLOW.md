# Level Builder META Workflow

## Scope and fixed rules

For META TOOL assignments, improve the reusable workflow and its tool handoffs. Treat named levels as evidence; take over their construction only when assigned.

Read project AGENTS.md and this skill. Use canonical Plastic MAIN and existing Unity/tool connections. Assume authorized Remote access for inspecting project assets and operating existing tools. Follow single-Editor/concurrency rules.

Build level content through Level Builder JSON and Layer0. Limit final manual work to small position/color/lighting refinements. Interpret "rebuild" as a NEW clean scene from the supported game template. For additions, use the supported additive import scope and verify preserved content. Generated Unity objects remain normally editable; recipes are one-time input, with no synchronization over later edits.

## Ordered workflow

1. **Prepare current context.** Obtain the current Copy for Chat package: destination/template, schema, request identity, import mode, usable asset IDs, Layer0 rules, camera/bounds and speed/coordinate conversions. Inspect real files, sprite previews/sub-assets, PPU, prefabs and animations through Remote as well as the catalog. For new art, follow [art-intake.md](references/art-intake.md): verify import facts, materialize declared animations, run the existing bounded incremental intake, wait for completion, and obtain an accepted/pending receipt with real catalog IDs. Register newly found assets through supported tooling. Never invent handles or reuse another scene's request IDs. If input is incomplete, inspect/refresh through existing routes or issue a precise tool-development task.

2. **Resolve units before positioning.** Read [units-and-evidence.md](references/units-and-evidence.md). Distinguish authoring coordinates, runtime coordinates and progression time. Use the level's effective signed runtime scroll velocity across placement, geometry, preview and QA. Verify the supported speed field and actual conversion code; retain source/target origins. A runtime-speed correction reported by another agent is not an applied code fix.

3. **Approve an achievable design.** Present two distinctly labeled images: inspiration and a composition made from inspected available asset images. Both are planning artifacts. Add a numbered plan mapping structures/routes to exact assets or missing-art requests, dimensions, physical/visual roles and intended animations. Preserve approved layout, style, depth and sense of scale. Obtain direction approval before building. Support branching/diggable routes and player splitting within verified camera/bounds behavior.

4. **Handle art gaps.** Prepare precise prompts/specifications for a dedicated art agent to produce and deliver missing sprites/animations. Use existing gameplay systems. Continue with conspicuous placeholders where feasible. Maintain a replacement ledger: scene/object or recipe placement, temporary asset, intended replacement, dimensions/PPU/pivot/frame requirements, owner and supported replacement action. Readiness with placeholders is allowed when this ledger is complete and limitations are disclosed.

5. **Build through the supported importer.** Use current Level Builder schema and automation. Inspect generated objects' actual Layer0 parenting/configuration; an empty backgroundLayers array is insufficient evidence. Verify real geometry/colliders and open/blocked/diggable routes. Test destructible damage/removal and opened paths. Inspect distinct existing ship-launch and shooting tower prefabs/components; verify behavior separately instead of inferring it from sprite/name.

6. **Capture, inspect, correct, review.** Run Level QA for the built scene. Read the actual manifest/index, tool response, PNGs and review status. Inspect the latest attempt and match scene/run/timestamp. Review both target fidelity and relevant Play Mode behavior. Keep import, compilation, capture, visual acceptance, gameplay and publication results separate. Correct within the approved JSON/tool route, then have an independent agent review matching QA artifacts and the approved design. Keep its findings and disposition.

7. **Create waves after the level works.** Obtain a fresh Reverse authoring/COPY AI package from the built scene. Create AND change wave content using JSON ONLY through the existing automatic Reverse tools. Validate/import with their current schema and real spawn/route bindings. Test integrated gameplay, spawn-relative spline behavior when applicable, progression timing and separate tower/wave spawn sources; review resulting QA.

## Evidence and completion

A "current state" image must be an actual matching Unity/Level QA capture. AI images, asset compositions and other levels' frames are planning/reference material. Never label them current or derive scene facts from them.

Preserve FAILED/NOT_REVIEWED, blank/missing captures, stale runs and timeout outcomes exactly. A framing/bounds workaround does not establish geometry/collider repair. Inspect captures visually; self-observation does not replace tool status or independent review.

Deliver: saved scene and recipe paths; resolved speed/conversion and expected/measured timing; matching QA run/images/status; gameplay results; independent review; exact placeholder replacements; and, after that stage, Reverse JSON/import/integrated QA results. Update the user at a good-result or blocker milestone, subject to session communication requirements.

If a capability is missing, send the tool developer a concrete task with minimal input, current code/tool identity, exact error/evidence, expected behavior and acceptance check. Do not silently replace the authoring pipeline with hand-placed content or new gameplay systems.
